# GNU Automake project-clean scope audit

Audited: 2026-08-19

## Product conclusion

**Audit complete; generic executable lane deferred.**

GNU Automake provides substantially more cleanup structure than an arbitrary handwritten Makefile: it generates standard clean-family rules and automatically knows about many generated outputs. However, Automake explicitly allows projects to widen those rules with additional file variables and project-defined `*-local` cleanup recipes.

Current Automake documentation allows projects to add:

- `MOSTLYCLEANFILES`;
- `CLEANFILES`;
- `DISTCLEANFILES`;
- `MAINTAINERCLEANFILES`;
- `mostlyclean-local`;
- `clean-local`;
- `distclean-local`;
- `maintainer-clean-local`.

The `*-local` targets are arbitrary Make recipes; Automake's own example uses `rm -rf` on a project-defined directory. Those recipes retain the full GNU Make execution model and can invoke arbitrary shell commands, scripts, recursive make, or paths outside a conventional build tree.

Therefore an Automake project cannot generically earn DevClean mutation authority merely because its clean targets were generated by Automake. The lane remains **REPORT_ONLY / deferred**, not AI review.

## Primary vendor contracts

Current GNU Automake documentation establishes:

- Automake generates standard clean-family rules and normally determines many generated files automatically;
- projects can explicitly widen cleanup through `MOSTLYCLEANFILES`, `CLEANFILES`, `DISTCLEANFILES`, and `MAINTAINERCLEANFILES`;
- when cleanup needs more than a hard-coded file list, projects can add arbitrary commands through `mostlyclean-local`, `clean-local`, `distclean-local`, and `maintainer-clean-local`;
- Automake documents `clean-local` with an example recursive directory deletion command;
- the different clean levels intentionally have different lifecycle scope: build outputs, configure-generated state, and maintainer-generated state are not interchangeable;
- generated `Makefile` execution still uses GNU Make, whose recipes and evaluation model are not a read-only declarative deletion manifest.

## Why Automake is not equivalent to generic Make -- but still not executable

The generic GNU Make audit concludes that a target named `clean` is arbitrary project-defined recipe execution. Automake improves on this by generating much of the normal cleanup logic from higher-level project declarations.

That distinction is real and useful for understanding the source. It is still insufficient for generic execution authority because Automake deliberately preserves project extensibility.

A valid Automake project can combine generated cleanup with project-defined extra files and arbitrary `clean-local` commands. DevClean cannot assume that the generated default portion is the complete destructive scope of `make clean`.

This is the same authorization principle used for Maven, Gradle, CMake, and MSBuild: a conventional vendor-provided clean path does not become executable when supported project configuration can widen its destructive behavior beyond the paths DevClean has proved.

## Additional clean-file variables widen path scope

Automake's clean variables intentionally let project authors add files to the generated clean-family targets.

A name listed in `CLEANFILES` or a related variable is project configuration, not a universal child of one known output directory. Effective values can depend on Make variables, configure substitutions, included fragments, and project layout.

DevClean must not:

- assume these values stay beneath the current build directory;
- parse one `Makefile.am` and ignore generated/effective configuration;
- treat conventional file suffixes or directory names as proof that the configured paths are disposable;
- silently drop user-configured clean entries and claim the result is equivalent to Automake clean.

## `clean-local` makes the complete behavior executable code

Automake explicitly supports project-defined `clean-local` and related local targets when cleanup requires more than deleting known file lists.

These local targets are Make recipes. They may run arbitrary commands and can therefore:

- recursively delete project-defined directories;
- delete outside the current build directory;
- invoke scripts/programs/package managers;
- recurse into other projects;
- perform non-filesystem side effects;
- consume environment/configuration state at runtime.

The existence of a generated Automake `clean` rule does not neutralize these extensions.

DevClean cannot grant generic execution unless it can prove that the **entire effective clean graph** contains no unbounded project-defined behavior.

## Why `make -n clean` remains unsuitable

An Automake-generated Makefile is still executed by GNU Make.

The generic Make audit already establishes that GNU Make dry-run is not a guaranteed read-only discovery primitive: recursive Make lines and recipes required to remake included makefiles may execute, and Makefile evaluation can itself invoke shell commands through functions such as `$(shell ...)`.

Automake does not provide a separate safe machine-readable "effective clean manifest" that bypasses this Make execution model.

DevClean therefore must not probe an Automake project with `make -n clean` and treat the printed recipe text as cleanup authority.

## Clean levels must remain semantically separate

Automake follows the GNU clean-family model:

- `mostlyclean` targets commonly rebuilt generated state;
- `clean` removes normal build-generated state;
- `distclean` additionally removes configure-generated state;
- `maintainer-clean` may remove maintainer-generated state.

These levels have materially different rebuild requirements and user impact. DevClean must never collapse them into a generic "deep clean" hierarchy based only on how much disk each appears to reclaim.

Even if a future narrow Automake lane becomes possible, each effective operation would need its own semantic and execution-scope proof.

## Out-of-source builds do not automatically solve the problem

Automake/Autoconf projects may support VPATH/out-of-source builds, but the mere existence of a separate build tree does not prove that every custom clean file or `clean-local` action is confined to that tree.

This differs from the already-audited Meson whole-build-tree lifecycle, where the vendor's design contract itself gives DevClean a separate exact configured build-tree object that can be deleted after USER_REVIEW.

DevClean must not transfer Meson's authority model to Automake merely because both projects happen to be configured out of source.

## Raw build-tree deletion is not a generic substitute

Blocking `make clean` does not authorize DevClean to delete the current Automake build directory recursively.

Automake projects can use in-source builds, VPATH builds, source-side generated files, configure-generated state, and custom cleanup configuration. A selected build directory is not universally equivalent to the complete disposable generated-state lifecycle.

No generic raw-directory fallback is granted.

## Revisit condition

A future narrower Automake executable lane would require a supported, non-executing, machine-readable effective cleanup model that completely accounts for the exact project configuration.

At minimum it would need to prove:

1. exact Automake/Autoconf project and configured-build identity;
2. the exact clean level being requested;
3. every generated cleanup path after all effective substitutions/variables;
4. absence or fully bounded semantics of `*-local`/custom cleanup recipes;
5. recursive subdirectory clean behavior across the whole project;
6. every affected path independently bounded to approved local storage;
7. no inventory step executes arbitrary project code;
8. identical scope immediately before mutation;
9. a vendor-owned operation or exact safe deletion primitive whose semantics match the proved scope.

If project-defined recipes remain part of the effective clean graph, generic execution remains deferred.

## Deliberate exclusions

This audit grants no authority to:

- invoke Automake-generated `make clean` generically;
- invoke `mostlyclean`, `distclean`, or `maintainer-clean` generically;
- run `make -n` as supposedly harmless cleanup discovery;
- parse only `Makefile.am` or only the generated `Makefile` into mutation authority;
- ignore `CLEANFILES`-family variables or `*-local` targets;
- execute project cleanup recipes to discover their behavior;
- recursively delete an Automake build tree as a generic fallback;
- use AI to interpret arbitrary local cleanup recipes and thereby grant execution authority.

## Product status

**GNU Automake generic clean-family targets = REPORT_ONLY / audited / executable action deferred.**

Automake's generated defaults are useful source semantics, but supported project extensions prevent a complete bounded generic clean authority.

Normal DevClean validation still applies to this documentation-only safety decision: lock/dependency checks, Ruff, strict mypy, full pytest/current workflow, Windows EXE artifact, and CodeQL must all remain green before merge.
