# Visual Studio IDE storage audit

DevClean treats Visual Studio's user-data tree as mixed IDE state. Only exact subtrees with source-backed regeneration semantics receive deletion authority.

Source-audited boundaries:

- Current Visual Studio extensibility documentation places the MEF composition error log inside `%LOCALAPPDATA%\Microsoft\VisualStudio\<instance>\ComponentModelCache`, confirming that `ComponentModelCache` is per-instance MEF composition state rather than project data.
- Microsoft troubleshooting guidance instructs users to close Visual Studio, remove/rename `ComponentModelCache`, and restart Visual Studio to rebuild/reset the MEF cache. Microsoft Q&A guidance repeats this boundary for Visual Studio 2022 (`17.0_<InstanceID>`) and Visual Studio 2026 (`18.0_*`).
- DevClean therefore recognizes only existing Visual Studio 2019/2022/2026 instance selectors (`16.0`, `17.0`, `18.0`, with optional hexadecimal instance suffixes) under `%LOCALAPPDATA%\Microsoft\VisualStudio` and delegates the exact `ComponentModelCache` subtree.
- Microsoft staff support guidance identifies `%LOCALAPPDATA%\Microsoft\VisualStudio\Roslyn\Cache` as Roslyn analyzer cache and states that deleting that cache does not affect Visual Studio functionality, although analyzer loading can be slower while it is rebuilt. A later Microsoft staff answer similarly lists the Roslyn location among Visual Studio local caches that can be removed.
- DevClean deliberately narrows that support guidance to the exact shared `Roslyn\Cache` subtree. It does not delegate the parent `%LOCALAPPDATA%\Microsoft\VisualStudio\Roslyn` directory or unknown Roslyn siblings, because the stronger source statement names `Roslyn\Cache` specifically.
- Both delegated rules require `devenv.exe` to be closed. A process-query failure is treated as "in use" rather than granting deletion authority. The Roslyn rule also uses a higher minimum reclaim threshold because rebuilding analyzer state can increase subsequent analyzer load time.
- The surrounding per-instance Visual Studio directory is not a cache boundary. Files such as `privateregistry.bin`, other per-instance state, settings, licensing state, extensions, and unknown siblings are not claimed by these rules.
- `%APPDATA%\Microsoft\VisualStudio\<instance>\ActivityLog.xml` is troubleshooting evidence generated by `devenv /Log`; it is deliberately outside these cache rules.
- Project-local `.vs`, `bin`, and `obj` directories remain project-owned and are not inferred globally from their names. MSBuild cleanup stays project-aware.

Conclusion: exact per-instance `ComponentModelCache` roots and the exact shared `Roslyn\Cache` root are `IDE_CACHE` / VENDOR_MANAGED / TOOL with a closed-Visual-Studio process guard. Their containing Visual Studio/Roslyn trees receive no generic recursive deletion authority.
