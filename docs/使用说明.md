# DevClean 使用说明

Windows 11 磁盘清理工具，专门针对**开发工具与 AI 软件产生的缓存**——pip、uv、npm、pnpm、Yarn、Docker、Android 模拟器、Ollama、Claude、Codex、JetBrains、VS Code 及其分支等。这些位置是通用清理软件基本不覆盖的，而在开发机上它们往往是占地方的主体。

## 装什么都不用装

`DevClean.exe` 自带 Python 运行时。不需要装 Python、不需要虚拟环境、不写注册表、不留后台服务。

双击 → 允许 UAC 提权 → 用完关掉即可。

**为什么要管理员权限**：`C:\Windows\Temp`、`SoftwareDistribution\Download`、`Prefetch`、ProgramData 下的错误报告队列，普通用户权限删不掉。不提权这些位置只能看不能删。

## 三步

### 1. 勾盘符，点「开始扫描」

右上角列出本机所有固定盘符，默认勾选系统盘（就是会被挤爆的那个）。

**不需要选文件夹、不需要选清理类别。** 该扫哪里是工具的事：它认识 61 个已知位置，并且明确知道哪些目录不该进（`.git`、`Documents`、`Program Files`、`site-packages`、OneDrive、凭据目录、系统区）。跳过这些让扫描少走 81 万条记录、快 30%。

### 2. 看两栏

| | 含义 | 怎么处理 |
|---|---|---|
| **可以删除**（左，绿） | 工具已经确定：已识别的厂商缓存根、确定性可再生的工具产物目录（`node_modules`、`__pycache__`、`.mypy_cache`、`.pytest_cache`、`.ruff_cache`）、超过配置天数（默认 1 天）的临时文件 | 直接清理 |
| **不确定，交 AI 判断**（右，橙） | 工具认不出这是什么 | 导出给 AI，导回结果 |

界面仍然只有两栏，不再增加第三个队列。程序或 AI 已确定不能删的项目由 KEEP 规则直接隐藏。只有 AI 明确回答 `UNSURE` 的项目才留在右栏，用户选中后可点“我来决定…”最终记为可删或保留。

### 3. 清理

左栏每行前面有方框，**默认全部勾选**。

- 点方框可以单独取消；点行的其他地方只是高亮，不影响删除
- 「全选」/「全不选」
- 标题数字跟着勾选走：全勾显示 `53.0 GB（6,816 项）`，取消一些后显示 `48.2 GB / 53.0 GB（已勾选 6,801 / 6,816）`

两个删除按钮：

| 按钮 | 行为 | 空间 |
|---|---|---|
| **清理（进回收站）** | 交给 Windows 回收站，可从资源管理器还原 | **不释放**，要清空回收站才释放 |
| **彻底删除** | 按文件句柄直接删除，无法还原 | 立即释放 |

**点了就删，不再弹二次确认。** 勾选 + 按按钮就是你的授权。

关于回收站有一件事必须知道：**Windows 在文件放不进回收站时（体积超过回收站配额、或该卷禁用了回收站）会静默直接删除**。DevClean 会在操作前后读回收站条目数来核对，没真进回收站就按"不可恢复"处理并报错，不会骗你说"可以还原"。

## 交给 AI 判断

1. 右栏点「导出给 AI」，存成 JSON
2. 把这份 JSON 交给任意模型（本地模型也行），文件里带了它该怎么回答的说明
3. 点「导入结果」读回

模型只能回三种结论：**KEEP（不能删）/ RECOMMEND_RECYCLE（可以删）/ UNSURE（不确定）**。判定可删的会移到左栏，仍需你自己点删除；`UNSURE` 会留在右栏。选中这些行并点“我来决定…”，弹窗会先显示 AI 对每一项的说明，再由用户决定：

- 选择“是”：写入 `USER_DECISION` DELETE 精确路径规则，移到左栏并勾选；实际删除仍需再点清理按钮。
- 选择“否”：写入 `USER_DECISION` KEEP 精确路径规则并隐藏。
- 选择“取消”：不作修改。

导出后即使关闭并重开 DevClean，也可以直接点「导入结果」，不需要先重新扫描或重新导出。用于恢复候选路径的会话索引集中保存在一个有上限的 JSON 中，最多保留 100,000 个候选路径；完整导入且没有遗留 `UNSURE` 时会移除对应记录。有 `UNSURE` 时保留记录，方便重启后再次导入并完成用户决定。

导出包含完整路径——本地模型看不到路径根本判断不了"能不能删"。要发给非本机模型的话自己先看一遍导出内容。

同一次运行中导入时使用完整封闭校验：候选 ID 必须一对一精确覆盖，编造的、重复的、遗漏的或摘要不匹配的一律整份拒绝。结果不会因为回答耗时而过期。程序重启后没有内存中的完整导出包，备用导入只接受持久索引中确实存在的候选 ID 和三种规定结论，并允许逐份导入部分答案。两种流程都不能让模型改路径、扩大范围或选择删除方式。

## 三份可编辑规则

首次启动会在 `DevClean-data\rules\` 创建：

- `scan-rules.json`：是否扫描用户目录、已知缓存位置及其分类策略、额外扫描路径、排除路径、跳过的目录名。
- `delete-rules.json`：确定可以删除的规则。AI 导入的 `RECOMMEND_RECYCLE` 和用户对 AI-UNSURE 项的“可以删除”决定会以 `exact_path` 规则写入这里。
- `keep-rules.json`：确定保留的规则。AI 导入的 `KEEP` 和用户对 AI-UNSURE 项的“确定保留”决定会以 `exact_path` 规则写入这里，并且始终优先于删除规则。

同一目录还会生成 `DevClean-default-rules-backup.zip`，里面是随当前版本提供的三份原始规则。规则编辑器中的“恢复默认配置”可以一键还原，用户也可以手工解压查看。

右上角“规则设置”可以直接编辑三份 JSON，也可以点击“打开规则文件夹”后用编辑器或 AI 审定。保存后 DELETE/KEEP 的 `rules` 立即重新应用；扫描范围、阈值和分类表从下一次扫描开始应用。

如果外部编辑导致 JSON 格式错误，“规则设置”会显示磁盘上的原始内容，用户可以直接在 UI 中修正，不会用默认配置遮住错误文本。

删除和保留规则的 `match` 支持：

- `exact_path`：一个完整路径。
- `path_prefix`：某个目录及其全部后代。
- `path_glob`：完整路径通配符。
- `filename_glob`：只匹配文件名，例如 `*.tmp`。
- `path_regex`：用正则表达式搜索完整路径。忽略大小写，路径分隔符统一写成 `/`。
- `filename_regex`：用正则表达式搜索文件名，忽略大小写。

正则表达式会在程序启动或 UI 保存时预先校验并编译。表达式有语法错误时整份配置不会生效，界面会指出具体是第几条规则；不会等扫描到一半才报错。

三份文件都有明确人工分组：

- 扫描规则用 `skip_directory_groups` 和每个已知根的 `group` 分类。
- DELETE/KEEP 的内部分列表用 `classification_groups` 分类。
- DELETE/KEEP 的每条路径规则都必须填写 `group`；AI 导入统一写入 `ai_import` 组，用户对 AI-UNSURE 项的最终决定写入 `user_decision` 组。

分组名称和分组顺序也保存在 JSON 中，保存规则或导入 AI 结论时会原样保留，不会被 Python 中的隐藏默认值覆盖。`classification_groups` 可以重新组织，但必须把对应 `classification` 的每个字段恰好列出一次。

每份文件还带有 `_ai_editing_contract`。给 AI 编辑时直接提供完整文件，合同要求它只返回完整 JSON、不得使用 Markdown、不得增删或改名字段、不得修改文档类型，并在不确定时不新增规则。程序不只依赖提示语：顶层、分类表、已知根和每条规则都使用严格字段白名单，多一个字段、少一个字段、重复 ID、无效枚举或无效正则都会整份拒绝。

例如，下面的删除规则可以覆盖任意用户目录中名称为 `Cache`、`Code Cache` 或 `GPUCache` 的目录内容，而不需要给每个文件保存一条规则：

```json
{
  "id": "browser-cache-directories",
  "group": "browser_cache",
  "enabled": true,
  "match": "path_regex",
  "value": "/(Cache|Code Cache|GPUCache)/",
  "source": "USER",
  "reason": "可重新生成的浏览器缓存目录",
  "updated_at": ""
}
```

一条手工规则的写法如下；`id` 只要在当前文件内便于辨认即可，`source` 使用 `USER`，不想删除规则时也可以先把 `enabled` 改成 `false`：

```json
{
  "id": "keep-my-build-output",
  "group": "project_overrides",
  "enabled": true,
  "match": "path_prefix",
  "value": "D:\\work\\important-project\\build",
  "source": "USER",
  "reason": "这是我需要保留的构建产物",
  "updated_at": ""
}
```

`scan-rules.json` 的 `include_known_cleanup_roots` 改为 `false` 后，本文件中配置的已知缓存路径即使位于用户目录下面也会从遍历中剪掉。已知清理目录、分类、策略和标签全部在本文件的 `known_cleanup_roots` 中管理。Windows、ProgramData 或 Windows.old 下确实允许清理的条目使用 `allow_inside_system_anchor: true`；没有这个标记的相邻系统路径仍会被执行层拒绝。

`delete-rules.json` 中的 `thresholds` 和 `classification` 是确定可删分类的唯一数据来源；`keep-rules.json` 中的 `classification` 是确定不删分类的唯一数据来源。两个文件的 `rules` 可继续添加精确路径、前缀、通配符或正则规则。执行层对 Windows 关键目录、本机固定卷、重解析点和文件身份的检查不是分类配置，不会被配置文件绕过。

AI 的明确删除/保留结论合计最多沉淀 100,000 条。AI 自己的 `UNSURE` 不直接写入删除或保留规则，仍会留在不确定列表；只有用户随后明确作出的最终决定才写入 `USER_DECISION` 规则。三份规则文件是后续扫描和分类的唯一配置，程序只接受当前 `schema_version=2`。

## 删除时的安全边界

不是靠"你确认过"，是靠删除那一刻的复核：

- 每个对象在删除前重新核对 **卷序列号 + 128 位 file ID + 大小 + 时间戳**。扫描和删除之间文件被替换掉就拒绝那一项，不会误删替换进来的东西。
- 整个目录作为一个对象删除时，遍历实现**不进入重解析点**——`node_modules` 里的 junction / 符号链接（`npm link`、pnpm 造的）按链接自身处理，不会把链接目标当作目标树的普通子目录继续遍历。
- 删除意图先写进 SQLite 日志再产生副作用；崩溃后不会自动重放。
- 某一项因占用、权限或扫描后变化而不能删除时，会记录失败原因并继续处理下一项；一次失败不会卡死整批清理。
- 只处理本地固定卷上的普通文件和目录，不碰网络盘、可移动盘、云占位文件。

## 已知限制

- 只支持 Windows 11 x64
- 回收站模式不释放空间，这是回收站的性质
- 整个目录删除**不是原子的**：中途失败或取消时，已删掉的部分无法恢复
- 扫描期间文件在变（比如缓存正在写），删除时会拒绝变化的那些项，属正常
