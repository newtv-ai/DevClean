# DevClean 架构与部署方案

## 一句话

三层单向依赖：**扫描（只读）→ 分类（判断，无副作用）→ 执行（唯一会删除扫描对象的地方）**。UI 只调用这三层，不保留另一套命令行产品入口。

```
scanner/filesystem.py        只读流式遍历，不下穿重解析点，可取消，带进度
        │  ScanRecord（file / directory / boundary / error）
        ▼
core/triage.py               分类：可以删除 / 不确定交 AI
core/cleanup_catalog.py      61 个已知位置 + 不该扫的目录名清单
        │  TriageItem
        ▼
core/postscan_cleanup.py     候选密封（HMAC）、成批、执行编排、身份复核
core/cleanup_journal.py      SQLite 意图日志（先写意图，再产生副作用）
        │
        ▼
platform/windows/exact_cleanup.py   句柄绑定的回收 / 删除 / 整树删除
```

`ui/app.py` 只负责呈现和收集用户动作，不含任何删除逻辑。

`core/user_rules.py` 管理 `DevClean-data\rules\` 下的三份公开 JSON 配置。`scan-rules.json` 保存扫描范围、剪枝目录和已知清理根；`delete-rules.json` 保存可删分类数据及 DELETE 规则；`keep-rules.json` 保存确定不删分类数据及 KEEP 规则。Python 只负责解析和执行这些规则，不保留第二套内置分类表；分组、帮助文字和 AI 编辑合同也从 JSON 读取并在保存时保留。三份文件使用严格字段白名单、唯一 ID、枚举和正则校验，并内含 `_ai_editing_contract`。AI 导入把明确结论写回 DELETE/KEEP 文件，每个文件独立原子替换，跨文件更新时先提交 DELETE、最后提交具有更高优先级的 KEEP。`ui/rule_editor.py` 是三份 JSON 的内置编辑界面。

首次创建规则时，同目录原子生成 `DevClean-default-rules-backup.zip`，内容直接取自同一套打包模板，不维护第四份规则源码。UI 可用该版本一键恢复三份默认规则。

跨重启 AI 导入的候选 ID/路径映射集中保存在 `DevClean-data\ai-sessions.json`，按最旧优先裁剪，最多保留 100,000 个候选路径。严格完整导入且没有遗留 `UNSURE` 时删除该会话在索引中的记录；若仍需用户最终决定则保留。

## 各层职责

### scanner/filesystem.py

- 流式产出 `ScanRecord`，不在内存里堆全量结果
- **不下穿**重解析点和云占位文件，各自产出 `BOUNDARY` 记录
- `ScanOptions.skip_directory_names`：在遍历边界直接不下降。目录本身仍被观察上报，里面一个字节不读
- `ScanOptions.exact_file_identity=False`（GUI 用）：普通文件从目录枚举数据成记录。给每个文件开句柄读 128 位身份要贵约 21 倍（实测 2,461 文件/s vs 52,347 文件/s），身份改在用户真正选中某个对象时才读

实测（本机 `%USERPROFILE%`）：不剪枝 1,767,404 条 / 121.3s；剪枝后 953,497 条 / 85.0s。

### core/cleanup_catalog.py

从 `scan-rules.json.known_cleanup_roots` 解析路径模板，只登记**实际存在**且在本地固定卷上的目录。路径支持大小写不敏感的 Windows 环境变量、通配符和花括号组合展开。系统目录中明确支持清理的根使用 `allow_inside_system_anchor` 标记，执行复核读取同一标记，不再维护第二份路径白名单。

`scan-rules.json.skip_directory_groups` 按版本库对象、用户文档媒体、凭据、装好的软件与环境、系统区等用途分组管理扫描剪枝名称；程序启动时把各组展开后交给 `ScanOptions.skip_directory_names`。

环境变量名由解析器按 Windows 语义忽略大小写，不要求用户在 JSON 中统一大写。

### core/triage.py

对每个观察给出两个出口之一：

| 出口 | 依据 |
|---|---|
| 可以删除 | catalog 已知根内（`known_root` 标签）、整目录候选（`whole_directory` 标签）、或确定性规则（超期临时文件） |
| 不确定，交 AI | 认不出来——这是 `_classify` 最后一个分支的兜底 |

AI 回答 `UNSURE` 后仍停留在“不确定”栏。UI 只允许对这些已经过 AI 的行执行最终用户决定：可删写入 `delete-rules.json`，保留写入 `keep-rules.json`，来源标记为 `USER_DECISION`；用户决定本身不触发删除。

**没有按路径形态写死的拒绝清单。** 曾经有过，它唯一的作用是把工具本已确定的东西降级——实测一条 `site-packages` 规则把 uv 缓存 517,757 个文件里的 436,283 个（84%）从"已识别厂商缓存"拽进"要问 AI"。产品变好的方向是扩大"确定"的范围，让需要问 AI 的越来越少。

分桶依据是"**有没有东西为它背书**"，不是 review lane。厂商缓存的 lane 就叫 `AI_REVIEW`（含义是"允许问 AI"），拿它分桶会把 pip 缓存整个推到不确定栏。

整目录准入只给两类：catalog 已识别的缓存根，或名字属于确定性可再生产物目录（`node_modules`、`__pycache__`、`.mypy_cache`、`.pytest_cache`、`.ruff_cache`）。`build`/`dist`/`out`/`target` **不在其中**——真实项目里这些名字也用于手写内容。

### core/postscan_cleanup.py

- 候选用 HMAC 密封（`_candidate_integrity`），构造后被改动即拒绝
- `prepare_cleanup_plan` 按位置切成每批最多 32 项的独立日志批次；**对选择数量没有上限**
- 同时选了目录和它内部的文件，在准备阶段就拒绝（在**整个计划**层面检查，因为两者可能落进不同批次）
- 执行前逐项复核：扫描根身份、批准根、本地固定卷、普通文件、非重解析、非云占位、卷序列号、128 位 file ID、大小、时间戳、句柄最终路径
- 硬拒绝只剩两类：系统关键目录、DevClean 自身状态目录
- **没有确认口令层**。勾选加按按钮就是授权

### platform/windows/exact_cleanup.py

唯一会回收或永久删除扫描对象的模块。

| 操作 | 实现 |
|---|---|
| 回收站 | 普通文件和整个目录分别按各自身份规则在句柄上核对 → `SHFileOperationW` + `FOF_ALLOWUNDO`。Shell 只吃路径（没有基于句柄的回收接口），因此核对与调用之间存在理论竞态；该竞态的结果是回收站里多一个可还原对象，而不是被销毁的对象 |
| 回收核验 | 前后读 `SHQueryRecycleBinW` 的条目数。Windows 在放不进时会静默直接删除，条目数没涨就报 `recycled=False`，调用方按不可恢复处理 |
| 永久删除 | `FILE_DISPOSITION_INFO_EX`（POSIX 语义，失败回退 `FILE_DISPOSITION_INFO`），处置绑定在已核验的句柄上。并发重命名可以改变可见名字，但换不掉正在被删的那个对象 |
| 整树删除 | 自底向上、显式栈、**从不进入重解析点**（链接按链接删除），因此遍历无法离开目标树。限制在批准根之内，句柄级复核 |

不存在 `os.remove` / `os.unlink` / `shutil.rmtree` / 宽范围命令的退路。

### core/cleanup_journal.py

SQLite，`journal_mode=DELETE`、`synchronous=FULL`、`BEGIN IMMEDIATE`。整批意图在第一个副作用之前提交。当前日志只有实际会产生的两种模式（回收站、永久删除）和对应状态，不包含旧隔离、恢复或 replay 状态机；完成批次最多保留 128 批。

## 构建与发布

### 从源码到 exe

```powershell
uv sync --frozen --python 3.13
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\build_windows_exe.ps1
```

产物在 `artifacts\windows-exe\dist\`：`DevClean.exe`（约 12 MB）+ `licenses\` 四份许可证文本。

PyInstaller 参数：`--onefile --windowed --uac-admin`。`--uac-admin` 让 exe 启动即申请提权——系统位置的垃圾没有管理员权限删不掉。

构建脚本自带的门禁：
- 产物必须落在专用 artifacts 子目录（否则抛错）
- 体积上限 50 MB
- `--ui-smoke`：打包前用同一 Python 3.13 环境构造真实 Tk 窗口再退出
- 构建流程不启动带 `--uac-admin` 的成品 EXE，避免 UAC 或无交互 CI 桌面卡住构建
- 成品 EXE 归档必须同时包含 `devclean.config` 资源包模块和三份默认规则，逐项缺失即失败
- 发布载荷必须恰好是 `DevClean.exe` 和四份许可证，出现本机规则、AI 会话、数据库或其他文件即失败
- 四份许可证文本缺一即失败

### 质量门禁

```powershell
uv run --frozen --python 3.13 ruff check src scripts
uv run --frozen --python 3.13 python -m mypy src scripts
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\build_windows_exe.ps1
```

仓库不再保留 Reclaimer 时代的 pytest、wheel/SBOM、gate evidence 或 broker
发布链。CI 使用一个 Python 3.13 Windows 作业执行上述静态检查并构建唯一交付物
`DevClean.exe`。

### 部署

单文件分发，没有安装程序、没有自动更新、未做代码签名（首次运行会有 SmartScreen 提示）。

## 现状与后续

**当前 1.0.0 实测**：本机 C 盘找出 53.0 GB 可以删除（6,816 项）、91.9 GB 需 AI 判断（1,718 项）。对照一个同类通用清理软件在同一台机器上找出 4.95 GB，其中 4.42 GB 只是两个 temp 目录。

当前版本已经支持在配置列明的自更新目录中识别被更高版本取代的旧版本目录；判断时每次重新读取同级目录，不缓存可能变化的版本结果。后续改进只需在有实际证据时扩充 `self_updater_parents` 和已知更新下载目录，不使用“所有版本号目录都可删”的宽泛规则。
