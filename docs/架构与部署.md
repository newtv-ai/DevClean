# DevClean 架构与部署方案

## 一句话

三层单向依赖：**扫描（只读）→ 分类（判断，无副作用）→ 执行（唯一会删除扫描对象的地方）**。UI 只调用这三层，不保留另一套命令行产品入口。

```
scanner/filesystem.py        只读流式遍历，不下穿重解析点，可取消，带进度
        │  ScanRecord（file / directory / boundary / error）
        ▼
core/triage.py               分类：可以删除 / 不确定交 AI
core/cleanup_catalog.py      从配置解析已知清理根和扫描剪枝
        │  TriageItem
        ▼
core/postscan_cleanup.py     候选密封（HMAC）、成批、执行编排、身份复核
core/cleanup_journal.py      SQLite 意图日志（先写意图，再产生副作用）
        │
        ▼
platform/windows/exact_cleanup.py   句柄绑定的回收 / 删除 / 整树删除
```

`ui/app.py` 负责呈现、收集用户动作和编排后台任务，不直接执行文件系统删除；
所有实际回收或永久删除仍只经 `core/postscan_cleanup.py` 进入 Windows 执行层。

`core/user_rules.py` 管理 `DevClean-data\rules\` 下的三份公开 JSON 配置。`scan-rules.json` 保存扫描范围、剪枝目录和已知清理根；`delete-rules.json` 保存可删分类数据及 DELETE 规则；`keep-rules.json` 保存确定不删分类数据及 KEEP 规则。Python 只负责解析和执行这些规则，不保留第二套内置分类表；分组、帮助文字和 AI 编辑合同也从 JSON 读取并在保存时保留。三份文件使用严格字段白名单、唯一 ID、枚举和正则校验，并内含 `_ai_editing_contract`。AI 导入把明确结论写回 DELETE/KEEP 文件：用户根和 AppData 根改写为环境变量，路径内用户名改写为 `%USERNAME%`；日期、时间戳、UUID、长哈希和生成型数字可形成受稳定路径约束的 `path_glob`。相反结论会撤销同形态通配规则；明确依赖文件年龄、当前状态或版本上下文的 DELETE/KEEP 只保存可移植精确规则。每个文件独立原子替换，跨文件更新时先提交 DELETE、最后提交具有更高优先级的 KEEP。`ui/rule_editor.py` 是三份 JSON 的内置编辑界面。

当前默认 `scan-rules.json` 有 33 条已知清理根记录和 65 个路径模板、6 个剪枝
分组；`delete-rules.json` 有 7 个分类分组和 458 条默认路径规则，
`keep-rules.json` 有 3 个分类分组和 45 条默认路径规则。503 条路径规则来自
用户已经付费取得并明确同意开源的 AI 审核结论，其中 446 条为可移植精确规则，
57 条为受稳定目录约束的同类动态规则；规则值不含生成时的用户名或
`C:\Users\...` 绝对用户路径。这里的数量是当前 1.0.0 默认配置快照，用户侧
活动规则仍以 EXE 旁 JSON 为准。

首次创建规则时，同目录原子生成 `DevClean-default-rules-backup.zip`，内容直接取自同一套打包模板，不维护第四份规则源码。UI 可用该版本一键恢复三份默认规则。

单文件 EXE 内的规则模板在 `DevClean-data\rules` 缺活动文件时用于首次复制；完整 sidecar 存在后，普通载入和规则编辑只读取 EXE 旁边的 JSON/ZIP。默认备份被单独删除时，程序会尽力从当前 EXE 自带模板重建 ZIP，但不会替换活动规则；打包资源暂时不可读或 ZIP 无法写入也不能阻断活动规则载入。缺失的活动规则优先从同目录备份补回。所有持久状态统一放在 `DevClean-data`；源码运行时也放在项目根目录的 `DevClean-data`，不写 AppData。

持久目录布局固定为：

```text
DevClean-data\
├─ rules\
│  ├─ scan-rules.json
│  ├─ delete-rules.json
│  ├─ keep-rules.json
│  └─ DevClean-default-rules-backup.zip
├─ ai-sessions.json
└─ state\
   └─ cleanup-journal.db
```

跨重启 AI 导入所需的会话随机值、包摘要和候选 ID/路径映射集中保存在 `DevClean-data\ai-sessions.json`，按最旧优先裁剪，最多保留 100,000 个候选路径。它不保存全量扫描结果。严格完整导入且没有遗留 `UNSURE` 时删除该会话在索引中的记录；部分答案或仍需用户最终决定时保留。

## 各层职责

### scanner/filesystem.py

- 流式产出 `ScanRecord`，不在内存里堆全量结果
- **不下穿**重解析点和云占位文件，各自产出 `BOUNDARY` 记录
- `ScanOptions.skip_directory_names`：在遍历边界直接不下降。目录本身仍被观察上报，里面一个字节不读
- `ScanOptions.exact_file_identity=False`（GUI 用）：普通文件从目录枚举数据成记录。给每个文件开句柄读 128 位身份要贵约 21 倍（实测 2,461 文件/s vs 52,347 文件/s），身份改在用户真正选中某个对象时才读

实测（本机 `%USERPROFILE%`）：不剪枝 1,767,404 条 / 121.3s；剪枝后 953,497 条 / 85.0s。

### core/cleanup_catalog.py

从 `scan-rules.json.known_cleanup_roots` 解析路径模板，只登记**实际存在**且在本地固定卷上的目录。路径支持大小写不敏感的 Windows 环境变量、通配符和花括号组合展开。系统目录中明确支持清理的根使用 `allow_inside_system_anchor` 标记，执行复核读取同一标记，不再维护第二份路径白名单。`delete_root_ids` 只引用这些已知根；默认只有 `windows-old`，使旧系统目录本身也能删除，其他缓存根仍作为扫描边界并只删除其中内容。

`scan-rules.json.skip_directory_groups` 按版本库对象、用户文档媒体、凭据、装好的软件与环境、系统区等用途分组管理扫描剪枝名称；程序启动时把各组展开后交给 `ScanOptions.skip_directory_names`。

环境变量名由解析器按 Windows 语义忽略大小写，不要求用户在 JSON 中统一大写。

### core/triage.py

对每个观察给出两个出口之一：

| 出口 | 依据 |
|---|---|
| 可以删除 | catalog 已知根内（`known_root` 标签）、整目录候选（`whole_directory` 标签）、或确定性规则（超期临时文件） |
| 不确定，交 AI | 认不出来——这是 `_classify` 最后一个分支的兜底 |

AI 回答 `UNSURE` 后仍停留在“不确定”栏。UI 只允许对这些已经过 AI 的行执行最终用户决定：可删写入 `delete-rules.json`，保留写入 `keep-rules.json`，来源标记为 `USER_DECISION`；用户决定本身不触发删除。

**分类层没有按产品名或用户目录形态写死的第二套 KEEP/DELETE 路径清单。**
配置化前的最终规则也没有 `.codex`、`.claude`、`site-packages` 等宽泛 KEEP
规则：认不出的内容进入 AI，而不是由宽泛路径规则假装确定不删。曾经有一条宽泛
`site-packages` 规则把 uv 缓存 517,757 个文件里的 436,283 个（84%）从
“已识别厂商缓存”拽进“要问 AI”，因此装好的程序载荷继续由 JSON 分类表处理；
AI 或用户明确判断后才写入可移植精确规则和受稳定路径约束的同类动态规则。
执行层仍保留不可由配置绕过的 Windows 关键目录、自身状态、卷类型、重解析点和
对象身份边界；这些是删除执行条件，不是隐藏的分类规则。

扫描按 `scan-rules.json` 的 `review_sample_per_category` 保留每个 lane/category 中体积最大的候选，原始产品值为 500；它同时约束界面审核队列和 AI 导出队列，避免把几万条小文件一次性交给付费模型。扫描中的预览每栏最多绘制 300 行，扫描完成后最多绘制 2,000 行。预览刷新间隔从上一次预览计算完成后开始，UI 事件按批处理并合并连续扫描快照，避免大扫描时旧预览排队使 Tk 窗口未响应。

AI 导出在这个样本之上再次做保守去重：仅将同一父目录、同一动态文件名模板，
并且分类、来源、lane、风险、证据、actionability、执行策略、恢复能力、说明、
标签、分配空间不确定性、硬链接重复标记、逻辑大小档和年龄档都相同的普通文件
合并为一个问题。整目录不属于 AI 候选；没有动态片段的语义文件名永远不合并。导出合同通过
`similar_path_group` 携带模板、数量、体积区间和时间区间，并要求模型只在结论
对全部成员一致时返回 DELETE/KEEP，否则返回 UNSURE；该字段也参与包摘要校验。
包内只向模型展示一个代表项，但本进程和跨重启索引都会保存候选 ID 对应的完整
成员路径；导入时每个成员分别写入精确结论，再按允许条件生成同一个保守
`path_glob`。若原因依赖当天、是否正在使用、年龄或版本，则不生成跨时间模板，
但当前已观察到的组成员仍全部得到精确结论。

合并后的问题每 300 个分成一份 JSON；超过 300 时按 `-1ofN` 等编号完整导出，
不截断候选。每卷有独立会话 ID、nonce 和包摘要，分别导入。

分桶依据是"**有没有东西为它背书**"，不是 review lane。厂商缓存的 lane 就叫 `AI_REVIEW`（含义是"允许问 AI"），拿它分桶会把 pip 缓存整个推到不确定栏。

整目录准入只给两类：catalog 已识别的缓存根，或名字属于确定性可再生产物目录（`node_modules`、`__pycache__`、`.mypy_cache`、`.pytest_cache`、`.ruff_cache`）。`build`/`dist`/`out`/`target` **不在其中**——真实项目里这些名字也用于手写内容。

### core/postscan_cleanup.py

- 候选用 HMAC 密封（`_candidate_integrity`），构造后被改动即拒绝
- `prepare_cleanup_plan` 按位置切成每批最多 32 项的独立日志批次；**对选择数量没有上限**
- 候选构造逐项上报准备进度；执行层逐项上报开始/完成状态，永久删除整目录时还转发底层逐目录累计的文件删除进度。进度回调只负责展示，回调失败不能改变删除结果。
- 同时选了目录和它内部的文件，在准备阶段就拒绝（在**整个计划**层面检查，因为两者可能落进不同批次）
- 执行前逐项复核：扫描根身份、批准根、本地固定卷、非重解析、非云占位、卷序列号、128 位 file ID 和句柄最终路径；普通文件另核对大小与时间戳，整目录核对扫描时的目录身份
- 硬拒绝只剩两类：系统关键目录、DevClean 自身状态目录
- **没有确认口令层**。勾选加按按钮就是授权

### platform/windows/exact_cleanup.py

唯一会回收或永久删除扫描对象的模块。

| 操作 | 实现 |
|---|---|
| 回收站 | 普通文件和整个目录分别按各自身份规则在句柄上核对 → `SHFileOperationW` + `FOF_ALLOWUNDO`。Shell 只吃路径（没有基于句柄的回收接口），因此核对与调用之间存在理论竞态；该竞态的结果是回收站里多一个可还原对象，而不是被销毁的对象 |
| 回收核验 | 前后读 `SHQueryRecycleBinW` 的条目数。条目数增加只能作为确认进入回收站的正证据；没有增加也可能是容量淘汰或并发修改，因此 `recycled=False` 只记为“源对象已移除但回收结果无法确认”。调用方移除已不存在的列表行、不计已释放空间，并提示可能无法恢复 |
| 永久删除 | `FILE_DISPOSITION_INFO_EX`（POSIX 语义，失败回退 `FILE_DISPOSITION_INFO`），处置绑定在已核验的句柄上。并发重命名可以改变可见名字，但换不掉正在被删的那个对象 |
| 整树删除 | 自底向上、显式栈、**从不进入重解析点**（链接按链接删除），因此遍历无法离开目标树。限制在批准根之内，句柄级复核 |

不存在 `os.remove` / `os.unlink` / `shutil.rmtree` / 宽范围命令的退路。

### core/cleanup_journal.py

SQLite，`journal_mode=DELETE`、`synchronous=FULL`、`BEGIN IMMEDIATE`。整批意图在第一个副作用之前提交。当前日志只有实际会产生的两种模式（回收站、永久删除）和对应状态，不包含旧隔离、恢复或 replay 状态机；无论成功、失败还是待复核，整个日志合计最多保留 128 批，不会因未完成记录无限增长。

## 构建与发布

### 从源码到 exe

构建机必须是 Windows x64，并安装项目锁定的 `uv 0.11.6`；Python 3.13 和开发
依赖由 `uv` 按 `uv.lock` 准备。这个要求只针对开发者，最终用户仍只运行 EXE。

```powershell
uv sync --frozen --python 3.13
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\build_windows_exe.ps1
```

产物在 `artifacts\windows-exe\dist\`：`DevClean.exe`（约 12 MB）+ `licenses\` 四份许可证文本。

PyInstaller 参数：`--onefile --windowed --uac-admin`。`--uac-admin` 让 exe 启动即申请提权——系统位置的垃圾没有管理员权限删不掉。

构建脚本自带的门禁：
- 产物必须落在专用 artifacts 子目录（否则抛错）
- 体积上限 50 MB
- `--ui-smoke`：打包前用同一 Python 3.13 环境构造真实 Tk 窗口再退出
- GUI 冒烟使用构建目录内的临时数据目录，结束后删除，不读取开发机已有的旧规则
- 构建流程不启动带 `--uac-admin` 的成品 EXE，避免 UAC 或无交互 CI 桌面卡住构建
- 成品 EXE 归档必须同时包含 `devclean.config` 资源包模块和三份默认规则，逐项缺失即失败
- 发布载荷必须恰好是 `DevClean.exe` 和四份许可证，出现本机规则、AI 会话、数据库或其他文件即失败
- 四份许可证文本缺一即失败

### 质量门禁

```powershell
uv lock --check
uv sync --frozen --python 3.13
uv pip check
uv run --frozen --python 3.13 ruff check src scripts tests
uv run --frozen --python 3.13 python -m mypy
uv run --frozen --python 3.13 pytest
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\build_windows_exe.ps1
```

仓库不再保留 Reclaimer 时代的测试、wheel/SBOM、gate evidence 或 broker
发布链。`tests\` 只覆盖当前 DevClean 的扫描、规则、AI 导入、删除编排和有界
日志。功能 CI 使用一个 Python 3.13 Windows 作业执行上述检查，并构建
`DevClean.exe` 加四份运行时许可证；另有独立的 Windows CodeQL 工作流做 Python
静态分析，不产生第二套产品或发布物。

### 部署

构建脚本只写 `artifacts\windows-exe\dist\`，不会静默覆盖仓库中的公开副本。准备
新版本时，在上述门禁通过后，把构建产物同步到 `release\`，再由用户实际运行
`release\DevClean.exe` 验收：

```powershell
Copy-Item -LiteralPath artifacts\windows-exe\dist\DevClean.exe `
  -Destination release\DevClean.exe -Force
Copy-Item -Path artifacts\windows-exe\dist\licenses\*.txt `
  -Destination release\licenses\ -Force
Get-FileHash -Algorithm SHA256 release\DevClean.exe
```

Git 跟踪和对外上传的 `release\` 载荷应恰好包含 `DevClean.exe` 和 `licenses\`
下四份文本。本机直接运行该 EXE 后会按产品设计在旁边生成被 `.gitignore` 排除的
`release\DevClean-data`；它可能含有用户已经付费取得的 AI 规则，不能因准备发布
而擅自删除，但也绝不能 stage 或上传。其他 AI 导出和数据库同样不得进入发布
载荷。CI 会把干净构建目录中的同一载荷上传为 `DevClean-Windows-x64` 构建产物，
保留 14 天。

程序本体是单文件 EXE，发布载荷另带四份许可证文本；没有安装程序、没有自动更新、
未做代码签名，首次运行可能出现 Windows SmartScreen 提示。提交和推送必须在
用户完成成品验收后进行。

## 现状与后续

扫描项数和体积由用户磁盘内容、活动规则和每个 lane/category 的 500 项保留上限
共同决定，不在代码或发布文档里承诺固定结果。历史实测与问题复现数据保留在审计
交接文档中，不作为当前版本对任意电脑的性能或清理量保证。

当前版本已经支持在配置列明的自更新目录中识别被更高版本取代的旧版本目录；判断时每次重新读取同级目录，不缓存可能变化的版本结果。后续改进只需在有实际证据时扩充 `self_updater_parents` 和已知更新下载目录，不使用“所有版本号目录都可删”的宽泛规则。
