# Ninja project-clean scope audit

Audited: 2026-08-19

## Product conclusion

**Audit complete; generic executable lane deferred.**

Standalone Ninja does not define one lifecycle-owned build directory whose contents are universally safe to remove. Ninja deliberately has very little policy about output placement: its own manual explicitly allows generated outputs to live beside source files or in a separate output tree, depending on the higher-level generator or project.

Ninja's vendor `-t clean` operation is semantically understandable, but its destructive scope is the effective build graph rather than one bounded directory. Current Ninja source shows that cleaning can remove:

- every non-phony edge output selected by the clean mode;
- all outputs of a multi-output edge even when only one target was named;
- recursively generated prerequisites for target-clean mode;
- edge `depfile` paths;
- edge `rspfile` paths;
- outputs discovered after loading existing dyndep files.

Those paths are not required by Ninja to stay beneath the directory containing `build.ninja`.

This is therefore a known execution-authority problem, **not AI uncertainty**. Generic standalone Ninja clean remains **REPORT_ONLY / deferred** until DevClean can obtain a stable, complete machine-readable pre-mutation clean manifest and independently bound every affected path.

## Primary vendor contracts

Current Ninja documentation and source establish the relevant boundary:

- Ninja is intentionally a low-policy build executor whose input files are normally generated by another build system;
- Ninja explicitly declines to choose whether build outputs live beside source files or in a separate output directory;
- `ninja -t clean` removes built files; default clean excludes outputs marked as generator outputs, `-g` widens that scope, target arguments recursively clean the named target's build chain, and `-r` cleans by rule;
- the clean tool honors Ninja's global dry-run `-n`, which implies verbose reporting;
- current `Cleaner::CleanAll` loads dyndeps, iterates graph edges, removes output nodes, and also removes depfile/rspfile paths;
- current target-clean recursively traverses generated inputs and removes every output of a multi-output edge;
- current `-t clean` implementation exposes only the ordinary command-line modes (`-g`, `-r`, target arguments); it does not expose a structured JSON/zero-delimited destructive manifest.

Primary sources:

- https://github.com/ninja-build/ninja/blob/master/doc/manual.asciidoc
- https://github.com/ninja-build/ninja/blob/master/src/clean.cc

## Why `build.ninja` does not create a cleanup root

The presence of a real `build.ninja` proves that Ninja can parse a build graph. It does **not** prove that every output belongs beneath the directory containing that manifest.

Ninja's own design documentation is explicit that projects and higher-level generators may choose either in-tree or out-of-tree outputs. A manifest can therefore name generated outputs, depfiles, or response files in source-side or otherwise external locations.

DevClean must not infer destructive authority from any of the following alone:

- a directory containing `build.ninja`;
- a directory named `build`, `out`, `ninja`, or similar;
- the fact that `ninja -t clean` is a vendor-supported command;
- the fact that a target is generated/rebuildable;
- the selected directory being on a local fixed volume.

The authorization question is the complete set of paths the exact clean invocation may remove, not whether the invocation is conventional.

## Why default `ninja -t clean` is not sufficiently bounded

The default tool excludes edges marked with Ninja's `generator` attribute unless `-g` is requested. That is useful lifecycle behavior, but it does not create a directory boundary for the remaining edges.

Current source performs roughly this destructive sequence for the selected graph:

1. load available dyndep information;
2. iterate relevant non-phony edges;
3. remove each selected edge output path;
4. remove that edge's configured depfile path;
5. remove that edge's configured rspfile path.

Any one of those paths can be outside a conventional build directory because Ninja itself does not impose the output-placement policy.

DevClean therefore must not expose default clean merely because it omits generator outputs, and it must never silently add `-g`.

## Target clean is not a safe narrowing shortcut

`ninja -t clean <target>` sounds narrower, but current Ninja source deliberately expands the operation beyond the literal named path:

- if the target is produced by a multi-output edge, **all** outputs from that edge are removed;
- the edge's depfile/rspfile are also removed;
- Ninja recursively walks generated input edges and cleans the build chain needed for the named target.

That behavior is correct for Ninja's build semantics, but it means an exact target name is not an exact destructive path authorization.

The same principle applies to `-r <rule>`: rule-based selection may cover many graph edges and their auxiliary files. It is not a DevClean per-file cleanup primitive.

## Why dry-run output is not enough for mutation authority

Ninja's clean tool honors global `-n` dry-run, and current source reports paths in verbose human text such as `Remove <path>` when those files currently exist.

That is useful diagnostic evidence, but DevClean should **not** promote it to a safety boundary for the generic lane because:

1. it is human-oriented output rather than a documented machine-readable destructive manifest;
2. dry-run reporting is conditioned on current file existence, so it is not a complete representation of every path encoded by the graph;
3. the real clean separately reparses the graph and reloads dyndep state, so the effective clean set can change if manifest/dyndep state changes between preview and mutation;
4. parsing text output would create a second fragile path grammar/escaping contract inside DevClean;
5. a safe local-disk cleaner must validate every possible destructive path, not merely the subset that happened to be printed in one preview.

DevClean should not parse `Remove ...` lines and claim that this proves the complete clean scope.

## Why `-t targets all` is not a complete clean manifest

Ninja does expose graph inspection tools such as `-t targets all`, but current clean source removes more than ordinary output nodes: depfiles and rspfiles participate as additional destructive paths, and clean loads dyndep information before selecting/removing files.

A list of graph target names therefore does not prove the complete set consumed by `Cleaner`.

DevClean must not combine several incomplete text tools and pretend that they reproduce Ninja's internal clean semantics.

## `cleandead` remains non-executable

Ninja also exposes `-t cleandead`, which uses historical build-log entries and removes outputs considered stale relative to the current graph.

That operation is even less suitable as a generic DevClean cleanup primitive: old log entries can refer to paths from previous graph versions, and a stale path still needs independent local ownership/scope proof before a local-disk product may mutate it.

No `cleandead` authority is granted by this audit.

## Higher-level generators retain their own authority model

Ninja is frequently generated by a higher-level build system. DevClean must preserve that higher-level semantic boundary instead of using Ninja as an escape hatch around an already-audited result.

Examples:

- **Meson-generated Ninja**: use the separately audited Meson configured-build-tree lifecycle. The exact Meson lane may remove the verified whole build tree after USER_REVIEW; it does not rely on generic Ninja clean scope.
- **CMake-generated Ninja**: the CMake project-clean audit remains deferred because CMake can widen clean behavior through generated metadata and additional clean files. Calling Ninja directly does not weaken that conclusion.
- other Ninja generators must be audited on their own source/lifecycle contract before mutation authority is granted.

A backend command cannot provide broader authority than the higher-level source that generated its graph.

## Revisit condition

A future generic Ninja executable lane requires a supported interface that provides a **complete machine-readable destructive plan** for the exact invocation and exact parsed graph.

At minimum DevClean would need to:

1. bind the exact Ninja executable/version and exact manifest identity;
2. obtain every path the clean operation may remove after all include/subninja expansion and dyndep loading;
3. include ordinary outputs, implicit outputs, depfiles, rspfiles, and any other current/future auxiliary paths consumed by Ninja's clean implementation;
4. distinguish default clean from generator-widened `-g`, target-clean recursion, rule-clean scope, and stale-log `cleandead` behavior;
5. reject unresolved, ambiguous, non-machine-readable, or dynamically changing clean scope;
6. normalize every path with Ninja-equivalent semantics and independently prove approved local storage/ownership;
7. re-obtain the same complete plan immediately before mutation and require an identity match;
8. invoke only the exact audited Ninja vendor operation after that proof;
9. verify postconditions without assuming the displayed logical file sizes equal physical reclaimed bytes.

If Ninja does not expose such a stable complete plan, generic standalone execution should remain deferred. A higher-level generator may still earn its own narrower executable lane independently.

## Deliberate exclusions

This audit grants no authority to:

- recursively delete a directory merely because it contains `build.ninja`;
- recursively delete directories named `build`, `out`, or similar;
- invoke `ninja -t clean` generically;
- invoke target/rule clean as a supposed exact-file deletion primitive;
- add `-g` automatically;
- invoke `ninja -t cleandead` as generic cleanup;
- parse dry-run `Remove ...` text into mutation authority;
- parse/reimplement arbitrary Ninja manifest syntax in DevClean to guess a clean plan;
- bypass CMake/Meson/other generator-specific safety decisions by calling Ninja directly;
- use AI to infer which Ninja outputs are safe or to invent a destructive command.

## Product status

**Ninja standalone generic clean = REPORT_ONLY / audited / executable action deferred.**

A supported decision to not expose a clean button is the intended product outcome until the complete destructive scope can be proven.

Normal DevClean validation still applies to this documentation-only safety decision: lock/dependency checks, Ruff, strict mypy, full pytest/current workflow, Windows EXE artifact, and CodeQL must all remain green before merge.
