## 2. 本轮确认并修复的问题

### 2.1 构建成功后仍被发布白名单判失败

原因：旧构建脚本运行成品 `--uac-admin` EXE 做 `--ui-smoke`，会在 `dist` 旁生成 `DevClean-data`。本轮清除 Python wheel 安装后，PyInstaller 的旧 `--collect-data devclean` 又只留下三份 JSON 数据而漏掉 `devclean.config` 包；`importlib.resources` 无法导入资源包，于是成品启动时报 `ModuleNotFoundError`，异常窗口等待关闭，看起来像构建卡住。

修复：GUI 构造冒烟在打包前使用同一 Python 3.13 环境运行真实 Tk 入口；PyInstaller 显式加入 `devclean.config` 隐藏导入和三份 JSON。构建后递归检查成品归档，资源包模块或任何一份规则缺失都会直接失败。GUI 冒烟使用构建目录内的临时数据目录，结束后删除，不会误读开发机已有的旧规则。

为什么这样改：只确认 JSON 文件名存在并不等于 `importlib.resources` 能使用；资源包代码和资源数据必须同时验证。用户收到的发布包仍只有 EXE 和许可证，三份可编辑规则仍由用户首次正常启动时在 EXE 旁生成。

### 2.2 “整个目录”可以彻底删除，却不能进回收站

原因：左栏可以出现整个缓存目录，但回收站实现只按普通文件打开和核对对象；目录缺少目录句柄语义，操作会被拒绝。事后核对也使用了文件比较函数，可能把仍存在的目录错误理解为路径被替换。

修复：

- 普通文件继续使用文件身份核对。
- 整个目录改用目录句柄、目录身份和最终路径核对。
- Shell 回收后，文件和目录分别使用对应的事后状态判断。
- 永久删除逻辑和用户点击“彻底删除”的语义不变。

为什么这样改：界面既然把“整个目录”放在左栏，两个清理按钮就都必须对它生效，不能出现功能前后矛盾。

### 2.3 AI 回答 UNSURE 后，用户没有最后决定入口

原因：原界面只会自动处理 `KEEP` 和旧命名的可删除结论。`UNSURE` 留在右栏，但用户不能把它最终判为可删或保留，不符合既定流程。

修复：右栏新增“我来决定…”：

1. 只有导入结果中明确回答 `UNSURE` 的行可以使用。
2. 用户先在右栏选中一项或多项。
3. 弹窗逐项展示路径和 AI 原因。
4. 选择“是”会写入 `USER_DECISION` DELETE 规则，移到左栏并默认勾选。
5. 选择“否”会写入 `USER_DECISION` KEEP 规则并隐藏。
6. 选择“取消”不做任何修改。
7. 最终用户决定只改变分类，不会自行触发删除；可删项仍需用户点击左侧清理按钮。

为什么这样改：流程必须是“程序确定 → AI 解释并判断 → AI 仍不确定才交给用户”，而不是让用户一开始就猜，也不能让 AI 的建议自动执行。

### 2.4 DevClean 可能扫描到自己的数据目录

原因：EXE 若放在 Downloads 等会被扫描的位置，旁边的 `DevClean-data` 没有进入默认剪枝。执行层会保护自身状态，但扫描层仍可能显示自己的临时写入文件，造成“看起来可选、执行时拒绝”的矛盾，并可能浪费 AI 判断次数。

修复：`scan-rules.json.skip_directory_groups.devclean_state` 保留可编辑的 `DevClean-data` 名称剪枝；扫描启动时还会把本次运行实际使用的 `data_dir()` 作为精确排除路径。因此 EXE 旁或源码工作目录中的 `DevClean-data` 都不会进入扫描，同时不会因为一个宽泛的 `DevClean` 名称规则而跳过用户其他同名目录。

为什么这样改：自身状态不应成为垃圾候选；同时继续遵守“所有扫描分类配置统一由三份 JSON 管理”。

### 2.5 残留代码、类型和注释不一致

- 删除整目录旧中转流程残留的未使用辅助函数和导出。
- 修正 SQLite 日志中关于当前回收站状态的过期注释。
- 修正 AI 会话路径计数的类型收窄。
- 修正规则编辑器父窗口类型。
- 整理导入和公开符号顺序。
- 同步更新使用说明和架构文档。

这些修改不改变用户产品决策，只清理已经确认的死代码、错误说明和静态检查问题。

### 2.7 本轮功能缺口收口与再次审计

本轮没有改变产品流程，只修正已经能从当前实现中证实的缺口：

- `Windows.old` 从 Windows Update 下载根中拆成独立已知根，并由
  `scan-rules.json.delete_root_ids=["windows-old"]` 明确允许删除根目录本身。
  Windows Temp、Prefetch、Windows Update 下载和 WER 仍只清理各自根内内容。
- AI 可删除结论从容易误解为“只能进回收站”的旧内部名称统一改为 `DELETE`；
  它仍只是分类建议，用户可以按既定设计选择回收站或彻底删除。
- 同一进程导入必须完整覆盖原导出包；只有真正重启后才允许部分答案。跨重启索引
  新增原 nonce 和包摘要，备用导入会同时比对会话 ID、nonce、摘要、候选 ID、
  规定结论和非空说明。
- KEEP 规则继续拥有最高优先级。若整个可删目录中存在被 KEEP 命中的已观察路径，
  整目录候选隐藏，只显示其余可删子项。
- 左栏不再同时显示整个目录和它的后代，避免用户取消勾选一个子文件后，它仍被
  已勾选父目录一起删除；回收空间统计也不再重复计算父目录和子项。
- 整目录候选在准备删除时会先比对扫描记录中的卷号、128 位目录 ID 和创建时间；
  同路径目录被替换会拒绝该项。界面只根据执行层明确返回的成功路径移除行，
  不再用可能吞掉权限错误的 `Path.exists()` 推测成功，因此失败项会保留供重试。
- 扫描过程不再保留 REPORT_ONLY 对象，不再保存全部已观察路径；每个
  lane/category 按扫描配置保留体积最大的候选，原始上限为 500，实时预览
  每栏最多绘制 300 行。
- SQLite 删除意图日志从“仅完成批次最多 128”改为“所有状态合计最多 128 批”，
  未完成或失败记录也不会无限增长；它仍不保存扫描结果。
- 删除未使用的 scan insights、旧进程提权检查、旧私有目录创建入口和无调用辅助
  类型；清除本机残留的旧测试字节码、旧模块字节码、空 schema 目录以及
  `release\DevClean-data`。

### 2.8 pytest 阶段确认的删除结果问题

用户在本轮明确授权：完成源码复审和修复后，为当前 DevClean 新建精简测试并运行
pytest；旧 Reclaimer 测试仍不恢复。

复审确认回收站执行存在一个结果语义错误：Shell 已经移除源对象时，旧行为仍把
行留在左栏；再次点击后，已不存在的路径又会被误记为已进入回收站。最初修复把
“源对象消失但回收站总条目数没有增加”直接解释为永久删除；后续 Claude 复审
正确指出，总数不增长也可能是旧条目被淘汰或回收站被并发修改，因此不能据此
证明永久删除。

最终修复：

- Shell 接受回收请求且源对象消失后，从左栏移除，不再提供无意义的重试。
- 回收站总条目数没有增加时单独记录为 `unverified_recycle_paths`，界面提示
  “已由 Windows 移除，但无法确认是否进入回收站，可能无法恢复”。
- 无法确认的对象不计入已释放空间；既不谎报可恢复，也不谎报一定永久删除。
- 删除准备失败和整批执行失败现在都计入“未完成”总数；整批失败按该批实际项目
  数量计数，不再只算 1 项。

当前 33 项功能测试覆盖三份规则、旧 schema 拒绝、正则与 KEEP 优先、AI
规则持久化和默认备份、AI 同轮完整导入、跨重启严格部分导入、扫描剪枝和预览
上限、单项失败继续、已消失项重试、回收站结果无法确认、Windows.old 根目录
进入整目录删除执行层、SQLite 128 批上限，以及相似 AI 问题合并与拒绝合并边界。

### 2.9 大扫描未响应与原规则迁移遗漏

用户在本机扫描到 74,247 个文件时，窗口显示“未响应”，右栏同时出现 28,644
个待 AI 判断项。复查确认是两个独立问题：

1. 扫描线程每 1.5 秒重新遍历全部候选生成预览，但旧代码在计算预览**之前**
   就设置下一次截止时间。只要一次预览超过 1.5 秒，下一条文件记录会立即再次
   全量计算。UI 又会一次性清空事件队列，并反复删除、插入每栏 2,000 行，
   因此旧预览越积越多，Tk 主线程不能及时处理窗口消息。
2. 配置化改动删除了原先“每个 lane/category 最多保留 500 个最大候选”的
   审核采样规则，导致所有未知小文件都进入 AI 队列，右栏从约 1,000 项膨胀到
   24,000 项以上。

修复后：

- `scan-rules.json` 新增 `review_sample_per_category: 500`，恢复配置化前的
  审核采样行为；扫描完成后对该样本执行规则、AI 导出和删除流程，界面最多
  绘制 2,000 行。
- 下一次预览的 1.5 秒间隔从本次预览**完成后**开始计算。
- UI 每轮最多处理 64 个事件；连续扫描进度和预览只呈现最新快照，完成、失败和
  删除事件仍严格保持顺序。
- 实时预览先按与扫描完成相同的整目录覆盖逻辑求有效项，再统计数量和体积，不再
  因分类桶创建顺序把整目录及其子文件重复计算。
- 事件泵的下一次 `after()` 调度放在 `finally` 中；单个畸形事件即使抛出异常，
  后续完成/失败事件仍能继续处理，不会让窗口永久停在忙碌状态。
- 删除不属于原规则的 5 条宽泛 `BASELINE` KEEP 规则；不再用新判断覆盖用户
  原有分类设计。
- 从 4 份已支付 AI 审核结果中严格恢复 205 条 DELETE 和 40 条 KEEP 结论；
  758 条 `UNSURE` 不伪造成确定规则。结论只写入本机
  `release\DevClean-data`，不进入开源默认配置；后续已迁移为环境变量路径和
  受约束的同类动态规则，详见 2.11。
- 真实只读扫描遍历 75 万多个文件后，AI 队列为 909 项，不再是 24,987 项。

### 2.10 删除进度停在“正在准备”

真实永久删除 5,593 项时，候选构造需要逐项打开句柄，而第一个整目录
`uv\cache` 又包含约 84,275 个文件。旧界面只在整个 32 项批次返回后更新一次，
因此执行层已经进入 `PURGE_PENDING` 并持续占用 CPU，界面仍显示“正在准备”且
进度条为零。回收站模式的候选准备阶段存在同样问题。

修复后：

- 候选构造每完成一项就上报 `已准备/总数` 和可处理数量。
- 永久删除逐项上报；整目录删除转发内部已处理文件数，进度条按当前项比例推进。
- 回收站准备阶段显示准确数量；进入 Windows Shell 后使用持续动画并显示当前
  第几项，因为该接口不提供可靠的目录内部逐文件计数。
- 所有进度回调均为非权威展示；回调异常不能停止或改变已经授权的删除。

### 2.11 AI 规则绑定本机路径，以及删除失败后定位困难

旧行为把 AI/用户结论保存为包含用户名和当时文件名的绝对 `exact_path`。换 Windows
账号、换电脑，或同类缓存第二天生成新的日期、UUID、哈希文件名时不能命中，会
重复消耗 AI 额度。删除失败后界面也只能显示长路径，用户必须手工逐级寻找。

修复后：

- 用户根、LocalAppData、Roaming、Temp 等改写为 Windows 环境变量，路径中编码
  的用户名改写为 `%USERNAME%`；转换不依赖当前电脑恰好登录原用户名。
- 日期、时间戳、UUID、长哈希和生成型数字 ID 可形成 `path_glob`；稳定目录和
  扩展名仍保留，不能退化为无边界的全盘通配。
- 同形态出现 DELETE/KEEP 冲突时删除通配模板，只保留可移植精确结论；后续再次
  导入同形态答案也不会让已冲突模板复活。
- 明确依赖“超过 N 天”“长期未使用”或“被更新版本取代”的 DELETE 不生成跨
  时间通配，避免把今天的新文件或当前版本套进旧结论。
- 本机已有 245 条付费 AI 结论已迁移为 245 条可移植精确规则和 53 条同类动态
  规则；逐条回验原结论 0 处变化，规则值中本机用户名由 245 处降为 0。
- 左右两栏都支持双击：目录直接打开，文件在资源管理器中选中，目标已不存在时
  打开最近仍存在的父目录。

### 2.12 规则设置错误读取 `_MEI` 临时目录

问题：三份活动规则已经位于 EXE 旁的 `DevClean-data\rules`，但 `load_rules()`
每次调用仍无条件读取一遍打包模板。单文件 EXE 的模板路径位于 PyInstaller
临时 `_MEI...`，该目录不可用时，点击“规则设置”会报“无法读取随程序提供的
初始配置”，即使同目录三份活动规则完全正常。

修复：

- 仅在活动规则确实缺失且同目录备份无法补回时读取 EXE 内模板并复制一次；
  单独缺少备份不影响活动规则载入，并会尽力从 EXE 内模板重新生成备份。
- 完整 sidecar 存在后，载入和编辑只读 `DevClean-data\rules`。
- “恢复默认配置”读取同目录 `DevClean-default-rules-backup.zip`；只有 ZIP 被
  单独删除时才重新读取当前 EXE 内模板重建，绝不覆盖活动规则。
- 源码运行的持久数据也改到项目根目录的 `DevClean-data`，不写 AppData。
- 新增回归测试：打包模板暂时不可读时活动规则仍可载入；恢复读取能力后，下一次
  载入会重建被删的备份，之后“恢复默认配置”重新可用。

### 2.13 长路径显示不全，以及同类文件重复消耗 AI 费用

问题：左右列表只能纵向滚动，长路径后半段看不到；右栏相似的动态文件逐条导出，
同一目录的一批时间戳、UUID、哈希或生成型数字文件会重复占用模型上下文和费用。
界面也没有直接提醒 AI 可能判断错误以及外部模型可能收费。

修复：

- 左右列表均增加横向滚动条，路径列保留完整内容；双击打开资源管理器的行为不变。
- 右栏常驻显示“AI 判断可能不准确，使用外部或付费模型可能产生费用”，并提醒
  导出文件包含本机完整路径，只应交给用户信任的模型。
- AI 导出仅合并同一父目录、同一动态文件名模板、同一分类/风险/证据/权限/说明、
  同一大小档和年龄档的普通文件；普通语义文件和任一条件不同的项目分别询问，
  不能为了省钱扩大结论。整目录由程序规则处理，不进入 AI 导出。
- 合并请求携带组内文件数、体积和修改时间范围，并严格要求 AI 仅在全部成员结论
  一致时回答 DELETE/KEEP，否则回答 UNSURE。
- 本进程及跨重启会话索引都保存候选 ID 对应的完整组成员；导入时每个已观察成员
  分别写入精确结论。即使年龄/版本理由抑制通配规则，也不会丢掉其余组员并再次
  收费。
- 导出状态显示原始文件数、实际 AI 问题数和减少的问题数。
- 明确依赖“今天/正在使用/当前版本”等上下文的 KEEP 与依赖年龄/旧版本的 DELETE
  一样只保存精确规则，避免将一次性的结论错误套到明天或其他版本。

### 2.14 Claude 对交接文档的复审修正

- 修复 AI 合并只记录代表路径的问题，覆盖同进程和跨重启导入。
- 修复实时扫描体积受分类桶顺序影响的问题。
- 修复事件泵遇到非 `Empty` 异常后不再调度的问题。
- 修复单独删除默认备份后无法在 UI 恢复的问题。
- mypy 配置改为 `mypy_path=["src"]`、`files=["src", "scripts", "tests"]`；
  直接运行 `python -m mypy` 不再出现找不到 `devclean` 包，并把当前测试一并
  纳入严格类型检查。
- 删除交接文档中已经被 2.9 推翻的“5 条默认 KEEP 路径规则”与打包证据。
- 删除“整目录会分别询问 AI”的错误表述；整目录本来就不属于 AI 候选。
- 回收站条目总数只能提供确认成功的正证据，不能提供永久删除的反证；相关状态、
  空间统计和用户提示已改为“结果无法确认”。

## 3. 当前实际产品流程

1. 用户勾选固定盘符并开始扫描。
2. 程序按 `scan-rules.json` 决定扫描位置、已知清理根和剪枝目录。
3. 程序确定可删的文件或目录进入左栏并默认勾选。
4. KEEP 项隐藏，不进入左栏，也不再询问 AI。
5. 程序不确定的普通文件进入右栏。
6. 用户导出 JSON 给 Codex、Claude 或其他模型。
7. 同一进程导入使用完整严格校验；重启后的备用导入保留允许部分答案的既定行为。
8. `DELETE` 写入 DELETE 规则并进入左栏；`KEEP` 写入 KEEP 规则并隐藏；`UNSURE` 留在右栏。
9. AI-UNSURE 项由用户通过“我来决定…”最终记为可删或保留。
10. 只有用户点击左栏“清理（进回收站）”或“彻底删除”才会执行文件系统变更。
11. 单项失败会记录并跳过，继续处理下一项；失败项仍留在界面，可再次点击重试。

## 5. AI 导入语义，后续不得混淆

### 同一次运行

保留完整导出包，导入时要求：

- 会话 ID、nonce、包摘要一致
- 所有候选一一对应
- 不能缺项、重复、编造候选
- 只能使用 KEEP / DELETE / UNSURE
- 每项必须有有界说明

### 程序重启后

完整内存包已不存在，使用 `DevClean-data\ai-sessions.json` 中的会话随机值、包摘要和候选 ID/路径映射恢复。这里按用户明确决定，允许只导入模型已经回答的部分；不能擅自改成“必须回答全部才接受”。备用导入仍必须比对会话、随机值和摘要，并严格校验每一条已回答记录。

无论哪种导入：

- 模型不能改路径或扩大范围。
- 模型不能选择回收站还是永久删除。
- 模型结论本身没有执行权限。
- 实际对象在删除时重新读取并核对。
- 严格完整导入若仍含 `UNSURE`，会话索引暂不删除，便于重启后重新导入并完成用户决定。

## 6. 用户明确决定：后续模型不得擅自违背

下面不是 Codex 的建议，而是项目所有者已经明确作出的产品决定。

1. DevClean 是 Windows 11 磁盘扫描和垃圾清理工具，不是云平台、企业后台或核安全系统。
2. 产品必须给普通用户直接使用，首选单文件 EXE；用户不能被要求安装 Python。
3. EXE 必须保持小，当前构建门槛为 50 MB，不能为了架构形式膨胀到几百 MB。
4. 需要实际 UI；当前 Tk GUI 可接受。
5. 程序自己确定可删的垃圾直接进左栏，不要求 AI。
6. 程序不确定的文件先交给 AI，AI 必须逐项解释是什么、为什么可删/不可删/不确定。
7. 只有 AI 仍不确定的项目才交给用户最后决定。
8. AI 导入后立即自动分类，不要求用户再执行一层“应用结果”。
9. AI 或用户确认可删，只是进入可删除规则/左栏，不会自动删除。
10. 用户点击“彻底删除”时，允许永久删除，包括 AI 推荐和用户最终确认的项目。
11. 用户点击删除按钮就是授权，不增加 `RECYCLE <scan-id>` 等口令。
12. 某个文件不能删除时必须自动跳过并继续下一个。
13. 删除中途失败后再次点击，必须能够重试仍存在的项目。
14. Windows Temp、Prefetch、Windows Update 下载、WER、Windows.old 中明确支持的垃圾必须能删除，不能只扫描不执行；放行范围仍由精确已知根控制。
15. AI 明确判决必须持久化；路径需对 Windows 用户名和常见动态日期/随机标识

    依赖文件年龄或版本相对关系的结论不得无条件扩大。
16. AI 明确判决最多保留 100,000 条。
17. 扫描、删除、确定不删统一由三份可编辑 JSON 管理；不要再放一套 Python 内置分类表。
18. 三份配置必须支持人工分组、正则、UI 编辑、严格 AI 编辑合同和默认备份恢复。
19. 不保留旧规则格式兼容层，避免叠床架屋。
20. 重启后的 AI 备用导入允许部分答案，这是用户明确保留的行为。
21. SQLite 只用于有上限的删除意图日志，不保存全量扫描结果；所有状态合计最多保留 128 批。不要把它改成庞大索引库。

## 8. 已知边界，不应伪装成已解决

- 当前没有代码签名，首次运行可能出现 Windows SmartScreen 提示。
- 回收站模式本身不释放空间；需要清空回收站才释放。
- Windows 可能在对象放不进回收站时永久删除；回收站总条目数也可能因淘汰或并发
  修改而不增长。DevClean 会把这种情况报告为“已移除但结果无法确认”，不会谎报
  一定可恢复或一定永久删除，也不会留下一个实际已不存在的失败项。
- 整个目录的永久删除不是原子操作；中途遇到占用项时，前面已删部分不会恢复。
- 本轮真实演练只使用专门创建的隔离样本，已经覆盖普通文件永久删除、占用失败后
  继续、重试、整目录、junction 边界和回收站；没有把用户真实缓存或 Windows
  系统目录当作测试数据，也没有模拟回收站容量不足的系统级条件。后续不得把它
  扩大描述成“已遍历所有真实缓存类型或所有 Windows 异常条件”。
